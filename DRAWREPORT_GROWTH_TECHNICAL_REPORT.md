## 1. Executive Summary

### Architecture in one paragraph
DrawReport is a single Python **Flask 3** monolith that server-renders every page with **Jinja2**.
There is no frontend framework: the browser runs four small vanilla-JS files
(`static/js/track.js`, `free.js`, `free_wait.js`, `free_result.js`). Data lives in **one SQLite
file** (`data/drawreport.sqlite3`, WAL mode, stdlib `sqlite3`, no ORM). Two long-running
**background workers** poll that same database: `worker.py` turns paid orders into PDF reports,
`free_worker.py` turns free uploads into short readings. Reports are generated by an LLM
(**Anthropic Claude**, provider-abstracted in `pipeline/llm.py`) and rendered to PDF with
WeasyPrint. Payment is **PayPal Orders API v2**. Email is SMTP (per docs: Brevo). Analytics is a
**first-party event store** (`events` + `web_visits` tables, fed by server-side calls and a
`/t/e` beacon) plus **GA4** and a **Meta Pixel** on the client.

### Especially relevant to marketing measurement
- **Three identity levels** exist in first-party data: visitor (`dr_v` cookie, 1 year), visit
  (`dr_s`, 30-minute sliding window), first-touch UTM (`dr_utm`, 1 year). Orders and free analyses
  both record `visitor_id` and `visit_id`.
- **Both first-touch and last-touch attribution are stored**: `events.utm_json` / `orders.utm_json`
  carry first touch; `web_visits.utm_json`, `web_visits.gclid` (gclid/fbclid/msclkid), `referer`
  and a derived `channel` carry the visit's own (last) touch.
- **Bots are a major data-quality issue**: per the journal, ~80% of recorded visits are bots and
  most remaining "human" rows are scanners. The only trustworthy human signal is
  `web_visits.engaged = 1` / the `engaged` event.
- **Volume is near zero**: per the journal (2026-09-08), 0 paid orders ever, 3 completed free
  readings, 2–6 engaged human visits per day. No rate metric is statistically usable yet.
- The first paid Facebook test started 2026-09-08 with a fixed UTM set (see §4).

Important nuances confirmed in code:
- The free funnel lives at `/free/…` **without** the locale prefix; everything else is under `/en/`.
- The order can be reached directly from the paid page **without** a free reading. The
  `orders.free_token` column and the `from_free` payload flag tell the two paths apart exactly.
- "Paid" in the admin visit funnel is counted from `orders.paid_at`, not from an event, because the
  webhook path has no browser and therefore no visit.
- `order_paid` is only emitted on the return-URL path. If the webhook wins the race, no
  `order_paid` event is written (the order row is still updated). Do not count sales from the event.

## 3. Existing Analytics and Tracking

### 3.1 First-party server-side + beacon analytics (the primary system)

| | |
|---|---|
| Name | DrawReport first-party analytics |
| Initialised | `app/__init__.py`: `app.before_request(track.before_request)`, `app.after_request(track.after_request)` |
| Files | `app/track.py`, `app/db.py` (`track()`, schema), `static/js/track.js`, `templates/_analytics.html` (script include), beacon route `routes.track_beacon` (`POST /t/e`) |
| Side | Server-side (route handlers call `track_event`) + client beacon (`navigator.sendBeacon('/t/e')`) |
| Persists | Yes, SQLite tables `events` and `web_visits`, no purge job |
| Cookies | `dr_v` visitor id (1 y, HttpOnly, SameSite=Lax); `dr_s` visit id (30 min, refreshed on every non-static request); `dr_utm` first-touch UTM JSON (1 y, set only when a UTM is in the URL and no cookie exists yet). All set server-side. No localStorage/sessionStorage use anywhere in `static/js` or templates |

**What `before_request` captures on every request** (`app/track.py`): visitor id (new or cookie),
visit id (new or cookie), `utm_source/medium/campaign/term/content` from the query string,
`gclid`/`fbclid`/`msclkid` (stored as `click_id` → `web_visits.gclid`, max 64 chars).

**What `web_visits` records** (one row per 30-minute visit, created at the first request that is
not `/admin`, `/static/`, `/favicon`, `/healthz`): `started_at`, `last_at`, `entry_path`,
`exit_path`, `pages` (HTML 2xx responses not in `NON_PAGE_PREFIXES`), `device`
(mobile/tablet/desktop/bot from UA), `channel`, `utm_json` (this visit's UTMs), `gclid`,
`referer` (300 chars), `geo_country`, `geo_region`; updated later by beacons with `engaged`,
`max_scroll`, `screen_w`, `is_touch`, and `customer_id` when a customer-linked event fires in
the visit.

**Channel classification** (`classify_channel`, evaluated once at visit creation, in trust
order): click id present → `ads`; `utm_medium` in cpc/ppc/paid/cpm/banner/ads/display/retargeting
→ `ads`; `utm_source` contains facebook/instagram/tiktok/pinterest/reddit/twitter/linkedin →
`social`; `utm_medium` email/newsletter → `email`; any other UTM → `utm`; no referer → `direct`;
referer host contains the site domain → `internal`; search host list → `organic`; social host
list → `social`; else `referral`.

**Bot detection** (`parse_device`): UA with `+http`, UA without `mozilla`, or matching a marker
list (bot, crawler, curl, python-requests, gptbot, ahrefs, facebookexternalhit, …) → `device='bot'`.
Admin screens exclude `device='bot'`. Detection is UA-only; headless browsers with a normal UA
pass as human.

**Event table columns** (`events`): `visitor_id`, `visit_id`, `customer_id`, `type`, `path`,
`payload_json`, `utm_json` (**first-touch**), `user_agent`, `device`, `referer`, `geo_country`,
`geo_region`, `geo_city`, `created_at` (UTC ISO-8601 string).

## 4. Existing Marketing Attribution Capability

Based only on `app/track.py`, `app/db.py`, `app/orders.py`, `app/free.py`, `app/admin*.py`.

| Capability | Answer | Why |
|---|---|---|
| User came from Facebook | **YES** | `web_visits.channel='social'` (utm_source contains facebook, or referer host facebook.*), or `channel='ads'` with an `fbclid` stored in `web_visits.gclid`. Journal caveat: raw `utm_source=facebook` counts are dominated by Facebook's link-preview fetchers; use `engaged=1 AND device<>'bot'` |

### Accuracy tiers

**Accurate immediately** (exists, stored, timestamped): visits, engaged visits, visitors, new vs
returning visitors, device/screen split, geo country, channel (last touch), UTM breakdowns (both
touches), free questionnaires/uploads/completions/failures by reason, free→paid pairs, orders
created, orders paid, gross revenue, coupon usage, order status pipeline, worker health, time to
generate (`elapsed_s`, `generated_at − paid_at`).

**Available but noisy**: anything counting all visits (bots pass UA filters; use `engaged`);
"checkout started" (proxy = `order_created`); sources of the home door in the admin Sources
table (it keys on `landing_view` only; the channels table covers both doors).

**Impossible today** (no data anywhere in the system): ad spend / CAC, PayPal fees, net
revenue, refunds, email opens/clicks, GSC impressions/clicks/queries/position via API, GA4 metrics
via API, Meta ad-level breakdown (fbclid → ad), page views per URL, time on page, experiment
variants, LTV beyond repeat orders (there are none yet).

**Need new tracking first**: refund status (webhook `PAYMENT.CAPTURE.REFUNDED` + column),
per-URL page-view event or counting `/en/blog/*` responses, cost import (manual or Meta/Google
API), GA4 Data API / GSC API service account and a nightly pull into a table, capture of Meta
ad/adset ids from the URL (Ads Manager dynamic parameters), fix of the `form_started` marker.

### Authentication approach
The existing admin auth is a shared password → HMAC cookie; unsuitable for a machine client.
Recommended: a dedicated long random bearer token in the server `.env` (e.g. a
`GROWTH_API_TOKEN` key), checked with `hmac.compare_digest`; endpoints disabled (404) when the
key is empty, exactly as `/admin` is disabled when `ADMIN_PASS` is empty; optionally restrict
`/internal/` in nginx to an IP allowlist; rate-limit; respond `Cache-Control: no-store`.

### Security concerns
- The DB contains children's names, parents' emails, free-text notes and links to drawings; the
  API must query only the whitelisted columns in §8 and never pass through `payload_json` for
  events like `order_form_errors` without filtering (payloads are small but unbounded).
- Enforce minimum group sizes for breakdowns (e.g. suppress buckets < 3) so a single Facebook
  click cannot be re-identified via geo + device + timestamp.
- Return aggregates and ratios only; no visitor ids, visit ids, tokens, order ids or emails.
- Add the routes to `track.NO_VISIT_PREFIXES` (as `/healthz` is) so a polling client does not
  create phantom visits.
- Read-only: open the SQLite connection with `mode=ro` (as `app/geoip.py` does).

### Can access be restricted to aggregated, non-PII data?
**Yes.** All identifiers needed for the metrics above are join keys, not outputs. The three
existing aggregation modules already produce dicts; the only leak points are
`admin_free_analytics.page_data()["pairs"]` (child name) and `surveys` labels (safe) — a thin
wrapper that drops `pairs`, `child`, `email` fields would be sufficient.

### Difficulty
**LOW** for summary/funnel/channels (reuse of existing modules + a token check + date range
parsing: the current `_period()` only supports 1/7/30/all, so `from`/`to` parsing is new but
trivial because timestamps are ISO strings compared lexically).
**MEDIUM** for content (needs a per-URL page-view source that does not exist yet) and for any
figure involving spend, GA4 or GSC (external API credentials and a nightly ingestion job on a
server with no cron).

## 12. Missing Measurement Gaps

Each gap is proven from inspection; the decision it blocks is stated.

**CRITICAL**
1. **No cost data anywhere.** Nothing stores ad spend (Meta, Google) → CAC, ROAS and
   cost-per-free-reading (the journal's own chosen metric) cannot be computed inside the system.
   Decision blocked: whether any paid channel pays back.
2. **Sample size ≈ 0.** Per journal: 0 paid orders ever, 3 completed free readings,
   2–6 engaged human visits/day. Decision blocked: any rate-based comparison (channel A vs B,
   page variant) — the infrastructure is ahead of the traffic.
3. **Bot contamination of top-of-funnel counts.** UA-only detection; journal shows ~80% of
   visits flagged bot and much of the rest scanners; Facebook's fetchers walk UTM variants. Only
   `engaged=1` is trustworthy. Decision blocked: honest visit-level CTR/CPC reconciliation with
   Ads Manager click counts unless the engaged filter is always applied.
4. **Refunds are invisible.** No refund state, no refund webhook. Decision blocked: net revenue,
   refund rate per channel, and whether the 7-day guarantee is being used.

**IMPORTANT**
5. **No per-URL page-view record.** `web_visits` stores entry/exit and a count; blog posts,
   samples and legal pages emit no server event. Decision blocked: which article actually earns
   attention and assists conversion (only "entered on" and "engaged on" are derivable).
6. **GA4 and Search Console data are locked in their UIs.** No API credentials, no pull, no
   table. Decision blocked: query-level SEO prioritisation and any automated organic report.
7. **Paid-vs-organic social cannot be split** when the ad reuses `utm_medium=social`
   (documented in the journal; fix is an Ads-Manager URL parameter, not code). Decision blocked:
   incremental effect of the boost vs. the page's organic reach.
8. **First-touch is UTM-only.** `dr_utm` is set only when a UTM is present; an organic or
   referral first visit leaves `events.utm_json`/`orders.utm_json` NULL and appears as
   "(direct / no UTM)" in the admin Sources table. Decision blocked: first-touch credit for SEO
   and referrals (last-touch is fine).
9. **Admin Sources table counts only `landing_view` visitors**, i.e. the paid door; home-door
   visitors by UTM appear only in the Channels table (by channel, not by campaign). Decision
   blocked: campaign-level performance of the free door from the existing screen (a query fixes
   it; the data exists).
10. **`form_started` funnel marker mismatch (likely bug).** `order.html` sends goal
    `form_started` → stored as `click:form_started`, but `admin_funnels.PAID_STEPS` matches the
    literal `form_started`. The step is therefore only ever lit by fill-in from deeper gates.
    Not confirmed at runtime; verify on the live admin. Decision blocked: real form-start rate.
11. **Checkout abandonment is unobservable.** PayPal's page is off-site; no `checkout_view` on
    the PayPal backend and cancel returns silently. Decision blocked: distinguishing "did not
    like the price" from "PayPal friction".
12. **`order_paid` event is path-dependent** (return URL only). Any event-based revenue count
    under-reports; must use `orders.paid_at`. Decision risk: a future API built on events would be
    wrong.
13. **Free-worker/email delivery has no outcome tracking.** SMTP send is fire-and-forget; no
    bounce/open data. Decision blocked: whether the "free_ready" email brings people back.

**NICE TO HAVE**
14. Meta ad/adset ids are not captured (only the five UTMs + click id).
15. No experiment/variant assignment mechanism.
16. No price-change log (live price edited in admin; only `orders.price_cents` remembers).
17. GeoIP snapshot has no refresh job; `geo_*` NULL before 2026-09-06.
18. Timezone is UTC everywhere; daily buckets will not match US local days in Ads Manager.
19. Meta Pixel has no Conversions API counterpart; browser blockers reduce Lead/Purchase counts.
20. `events`/`web_visits` never purged; fine today, but growth of the single SQLite file should be
    watched (all three processes write to it).

## 15. Final Assessment

| Dimension | Score | Rationale |
|---|---|---|
| **CURRENT MEASUREMENT READINESS** | **6/10** | Unusually complete first-party model for a site this size (visit + visitor + first/last touch, nested funnels, upload-failure reasons, free→paid linkage). Loses points for bot noise, no per-URL page views, no cost, no refunds. |
| **API READINESS** | **6/10** | SQLite plus three existing aggregation modules that already return dicts; summary/funnel/channels are a thin wrapper away. No auth mechanism for machines yet; content and external-data endpoints need new ingestion. |
| **ATTRIBUTION READINESS** | **6/10** | UTMs, click ids, referer, channel, first and last touch all stored and joined to orders and free analyses. Held back by UTM-only first touch, paid/organic social ambiguity, no ad-id capture, and no spend. |
| **SEO DATA READINESS** | **3/10** | Technical SEO is solid (canonical, sitemap, schema, robots, redirects, llms.txt), but every search *metric* lives only in GSC/Bing/Ahrefs UIs. Organic conversions are measurable first-party; queries and rankings are not. |
| **CONVERSION DATA READINESS** | **7/10** | Every commercial step from questionnaire to delivered PDF is a row with a timestamp and a source; revenue is joined to source. Deductions: refunds/fees absent, checkout is a black box, event-based `order_paid` is unreliable. |

### The 5 facts a growth strategist must know before designing experiments

1. **There is almost no signal yet.** As of 2026-09-08: zero paid orders in the site's life,
   three completed free readings, single-digit engaged human visits per day. The first
   experiments must be designed to produce *any* conversions, not to compare rates.
2. **Filter everything by `engaged = 1` and `device <> 'bot'`.** Raw visit counts are
   dominated by scanners and Facebook's own link fetchers (which even walk truncated UTM
   values). Ads Manager "clicks" will never reconcile with raw `web_visits`; they may with
   engaged visits.
3. **Two attribution models are stored; say which one you mean.** Last-touch lives on the
   visit (`web_visits`, joined by `visit_id` from orders and free analyses, includes
   fbclid/gclid and channel). First-touch lives in a 1-year UTM cookie and is blank for
   organic/referral first visits. Revenue can be split by either.
4. **The free reading is the real conversion event and is fully instrumented; the paid sale
   is measured from the order row, not from events.** Cost per started free reading
   (`free_analyses.uploaded_at`) is the metric the owner already chose; use `orders.paid_at`
   for sales. `orders.free_token` gives an exact free→paid link when the parent clicks through.
5. **Cost, refunds, GSC/GA4 metrics and per-article page views are outside the system.**
   Any experiment that needs CAC, net revenue, query-level SEO data or article read counts
   needs new tracking or an external data pull first; everything else in §11 can be queried
   today from one SQLite file.
